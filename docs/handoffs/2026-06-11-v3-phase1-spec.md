## Item model (the core v3 decision)

The SRS tracks **items**, not raw cards. An item = one knowledge unit (a dish's
components; one service fact). The prompt ladder (MC → cued recall → free
recall) is a *presentation mode* of the same item, chosen by session logic —
not separate scheduled cards. New namespaces (`dish:*`, `service:*`) are minted
for v3 items; the 428 frozen v2 engine card ids stay byte-frozen and are reused
only as *content material* (the `components:<foodId>:pick` MC card supplies the
MC rung's choices/distractors).

```ts
// src/lib/journey/types.ts
type ItemKind = 'dish' | 'service';
interface JourneyItem {
  id: string;            // 'dish:tuna-crudo' | 'service:seat-1-left'
  kind: ItemKind;
  unitId: string;
  foodId?: string;       // dish items: key into data.foods
}
```

## Unit 0 `service:*` items (authored content; source: SG/OB extracts in docs/handoffs/2026-06-10-service-extract.md + onboarding-deep-extract.md)

Each has: prompt, answer, 3 distractors (MC rung), cued hint, `why` (source
line). Author from these verbatim facts:

1. `service:seat-1-left` — Seat 1 is always to your LEFT as you approach the table; seats go clockwise.
2. `service:seat-1-middle` — Middle-of-room tables: approach so seat 1 is on the left with its back to the kitchen.
3. `service:seat-1-banquette` — Seat 1 will always be on the banquette.
4. `service:seat-0-shared` — Shared dishes are rung under seat 0.
5. `service:tables-bar-top` — 101–108 = bar top (101 nearest the front).
6. `service:tables-bar-tables` — 121–126 = bar tables.
7. `service:tables-loft` — 131–135 = loft (by the front door).
8. `service:tables-east` — 201–212 = east section (+221 high top).
9. `service:tables-west` — 301–309, 311–316, 321–326 = west section.
10. `service:tables-pdr-patio` — 401 = PDR, 141–144 = patio.
11. `service:no-auction` — Deliver by seat number; NEVER auction off food.
12. `service:romance-formula` — Romance the dish: introduce the NAME + 3 components. ("This is our grilled octopus salad with fennel and orange in a sherry soy vinaigrette.")
13. `service:fifo-drinks` — FIFO: first drinks made are first delivered, regardless of whose table; any drink sitting >1 minute, anyone runs it.
14. `service:priority-one` — Food & beverage running is always priority #1 (hot food hot, fresh cocktails fresh); #2 is clearing/resetting.
15. `service:allergy-every-item` — An allergy is noted on EVERY item that seat orders + all shared seat-0 items (stations print separately).
16. `service:open-hand` — Never point — open hand; excuse yourself when reaching; never reach across a guest.

## Module contracts

### `src/lib/srs/scheduler.ts` (Task B) — ts-fsrs v5 wrapper
- `type Rank = 'new' | 'learning' | 'solid' | 'locked-in'`
- `type Grade = 'again' | 'hard' | 'good' | 'easy'`
- `interface ItemSrs` — plain-JSON serializable (fsrs card fields + `lapses`, `reps`).
- `newItemSrs(now: Date): ItemSrs`; `reviewItem(s, grade, now): ItemSrs`;
  `isDue(s, now): boolean`; `dueAt(s): Date`; `rankOf(s): Rank`.
- fsrs config: `request_retention: 0.92`, short-term/learning steps enabled so
  the first review lands same-session and graduation yields a ~1d→2d→4d→7d-shaped
  early ladder. Rank mapping: new = never reviewed; learning = reviewed but
  young; solid ≈ scheduled interval ≥ 3.5d; locked-in ≈ ≥ 12d. A lapse ('again')
  on a solid/locked-in item must demote the rank (FSRS stability drop does this;
  assert it in tests). UI exposes RANKS ONLY, never intervals.

### `src/lib/store/` (Task C) — persistence
- idb database `bb3` (via `idb`): object stores `items` (itemId → {srs: ItemSrs,
  lapses, correct, lastGrade, introducedDay}), `meta` (streak {current, lastDay,
  freezesUsedWeekOf}, settings {lessonsPerDay: 8}, unitDone {unitId → 'gate'|'test-out'},
  dayLog {dayNumber → {reviews, newItems}}).
- Compact full-state snapshot mirrored to localStorage `bb3_progress_v1` on every
  write (iOS idb corruption fallback); load = idb first, mirror fallback.
- `navigator.storage.persist()` requested once post-load (browser only).
- `progress.svelte.ts`: Svelte-5 runes singleton exposing loaded state +
  mutations: `recordReview(itemId, grade, now)`, `introduceItem(itemId, now)`,
  `completeUnit(unitId, via)`, `tickStreak(now)` (one FREE freeze/week:
  a missed day auto-consumes the freeze instead of resetting), derived:
  `dueItems(now)`, `newToday(now)`, `rankCounts()`, `shakyItems()` (lapse-ranked).
- Fresh start — NO v2 import. SSR/test-safe: in-memory fallback; tests use
  `fake-indexeddb`.

### `src/lib/journey/` (Task D) — content model
- `stages.ts`: the table above as data. Stage/unit defs with title, blurb,
  track colour key (`food`).
- `service-items.ts`: the 16 authored items (full content: prompt, answer,
  choices, hint, why).
- `items.ts`: `itemsForUnit(unitId): JourneyItem[]`; for dish items, content
  accessors deriving from `data.foods`: `mcFor(item)` (reuse engine
  `generateDeck('components', data)` card matched by sourceId), `cuedFor(item)`
  (dish name + component count + first-letter hints), `freeFor(item)` (official
  `ingredients` list + `description` as the reveal), allergen chips + the
  `data.confirm.allergens` line on every teach/reveal surface.
- `gating.ts`: `unitStatus(unitId, progressView)` → 'locked'|'available'|
  'started'|'complete'. Unit complete = ≥85% of items at rank ≥ learning OR
  recorded test-out. Units unlock sequentially within a stage; checkpoint
  unlocks when all units complete; stage test-out = pass checkpoint cold (≥85%)
  → marks every unit + stage complete. Stages unlock sequentially.

### `src/lib/session/` (Task E) — pure state machine (no UI, no storage)
- `createLearnSession(items, deps)` → phases: `pretest` (one MC guess/item,
  instant reveal, NO srs effect) → `teach` (item screens in order) → `quiz`
  (test-to-criterion: ladder MC → cued → free; an item graduates at **3 correct
  recalls in the session**; a miss recycles the item into the queue ~3 positions
  later and resets nothing else; on graduation emit `introduce` + grade event).
- `createReviewSession(dueItems)` → retrieval ONLY; rung from rank (learning →
  cued, solid/locked-in → free recall); miss → emit 'again', inject that item's
  teach screen next, recycle until answered correctly (session "cleared").
- `createCheckpointSession(items)` → graded mix (cued/free), no teach, no
  recycling; result = score; pass ≥ 85%.
- Deterministic via injected `rng`; emits `onResult(itemId, grade)` events the
  caller forwards to the store. Self-graded reveal = the UI tells the session
  `gotIt: boolean` (binary → 'good'/'again'); 'hard' reserved for the allergen
  confidence flow (Stage 2).

### Routes (Tasks F–K)
- `/` Path · `/today` Today · `/playbook` (+ `/playbook/cram` print page) ·
  `/progress` · `/unit/[unitId]` learn-session runner · `/review` daily review
  runner · `/checkpoint/[stageId]` · `/preshift` (2-min shaky mode: top ~12
  lapse-ranked shift-critical due-or-shaky items).
- Today: Reviews button (count, never capped, finishable) THEN Lessons button
  (next unit in path, throttled to `lessonsPerDay` new items/day); streak +
  freeze chip; pre-shift entry. Path: vertical stage→unit journey, one strong
  accent (track colour), unit nodes show rank-meter fill; test-out affordance
  per unit; locked stages preview. Playbook v1: search + category-filtered
  dish cards (official components/allergens/description/price + confirm line)
  + cram print page.
- Design: tokens in `app-v3/src/app.css` only (semantic layer); Oswald
  lowercase h1/h2; track colour for Stage 1 = orange accent; flashcard faces =
  `.flash` paper scope (black-ink-on-cream both themes); axe both themes must
  pass; no generic-AI gradients; photo slots with graceful no-photo state
  (photos land in `static/img/<foodId>.webp` + `static/img/manifest.json`).
